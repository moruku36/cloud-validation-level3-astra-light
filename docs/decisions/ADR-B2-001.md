# ADR-B2-001：アプリ内製認証（ECS/PostgreSQL）の正式採用とCognito代替

- **ステータス**: 採択（Accepted）
- **日付**: 2026-09-10
- **関連要件**: REQ-02（認証・認可）、REQ-03（通知メール）、REQ-08（国内限定保存）、REQ-12（予算10万円/月）、REQ-13/14（専任1名運用体制）、REQ-16（個人情報保護・秘密情報）
- **置換対象**: [ADR-A2-001](ADR-A2-001.md) の D05（Cognito Lite採用）を破棄・置換（Supersedes ADR-A2-001 D05）

---

## 1. コンテキストと背景

A-2初期設計では、マネージド運用の利点を重視して Amazon Cognito Lite を採用していた。
しかし、Phase B における3社比較（B-1）、条件別設計（B-2）、および評価（B-3）を通じて以下の課題が顕在化した：
1. **将来コストの急増リスク**: 将来ユーザー数100万人・MAU拡大時に、外部IdPやCognitoのMAU課金が月額予算（初期10万円）を超過・圧迫する強い不確実性がある。
2. **データ主権と国内保存の厳密性**: 認証情報・メタデータ・ログが日本国外リージョンへ転送・複製されないことの完全な検証・監査が要求される（REQ-08）。
3. **トランザクション整合性**: プロフィール更新・お気に入り登録・退会時の即時整合性とSQLトランザクション連携を確実に担保する必要がある。

## 2. 決定事項

**Amazon Cognito の利用を取りやめ、Webアプリケーション内製認証（Django標準auth相当＋PostgreSQLサーバーサイドセッション）を正式採用する。**

| 項目 | 採用仕様 |
|---|---|
| **実装方式** | フレームワーク標準のセキュア認証ライブラリ（Django標準auth候補） |
| **暗号化・ハッシュ** | PBKDF2またはArgon2id（標準ライブラリ準拠、独自暗号方式は作らない） |
| **セッション管理** | PostgreSQL上のサーバーサイドセッションテーブル、HttpOnly/Secure/SameSite cookie |
| **パスワードリセット / 通知** | Amazon SES 東京リージョン経由（DB outboxパターンによる非同期キューイング） |
| **認可制御** | 認証ユーザーIDからowner scopeを導出、管理者権限は別ロール＋MFA強制 |

## 3. 利点とトレードオフ

### メリット
- **コスト抑制**: 追加のSaaS/IdP課金が一切発生せず、ECSとRDSの基本料金内に収まる（REQ-12適合）。
- **国内完結の確実性**: すべての認証データ・セッション・ログが東京リージョンのVPCおよびPostgreSQL内に閉じる（REQ-08適合）。
- **強いトランザクション整合性**: 退会処理時の即時論理削除・物理削除台帳連携が同一DBトランザクションで完結（REQ-07/16適合）。

### トレードオフと課題（指摘 F07 への対応）
- **運用保守負担（F07 / REQ-13）**: セキュリティパッチ適用、ブルートフォース攻撃防御（Rate Limit / WAF連携）、セッションローテーション等の保守責任が自社（専任1名）に帰属する。
- **今後の対策**: WAF Rate Limitルールとの併用、フレームワークの長期サポート（LTS）版固定、およびPhase Cでの認証ガードテスト（C-1にて36件実装）によりリスクを極小化する。
