クラウド検証 LEVEL3の要件定義をお願いします。

やりたいことの概要は以下です。

LEVEL3は、前回のLEVEL2のような「要件がある程度決まっていて、それを正しく実装できるか」ではなく、

曖昧なビジネス要件や制約から、どんなクラウド構成にすべきかをAI自身が判断できるか

を試す検証になります。

今回のLEVEL2では、かなり明確に

2台のVM
LB
Terraform
OIDC
Remote State
Monitoring
cleanup

というゴールがありました。

LEVEL3では、ここをあえて曖昧にします。

例えば、

月間100万PV程度のWebサービスを新規構築したい。
可用性は99.9%以上。
個人情報を扱う。
開発チームは5名。
運用担当は1名。
月額インフラ費用は10万円以内に抑えたい。
将来的に10倍程度までアクセスが増える可能性がある。
障害時は30分以内に復旧したい。
AWS / Azure / GCPのどれを使うかも含めて提案してほしい。

くらいしか伝えません。

ここからAIに、

どのクラウドを選ぶか
VMかコンテナかServerlessか
Kubernetesを使うか
SQLかNoSQLか
Multi-AZかMulti-Regionか
CDNを使うか
WAFを使うか
Backup / DRをどうするか
RTO / RPOをどう設計するか
Observabilityをどこまで入れるか
コストと可用性のトレードオフ
Security設計
IAM設計
IaC構成
CI/CD
運用体制

まで決めさせます。

ここがLEVEL2との大きな違いです。

LEVEL2とLEVEL3の違い
LEVEL2LEVEL3		
主目的	実装できるか	設計判断できるか
要件	比較的明確	曖昧
クラウド	指定	AIに選ばせることも可能
サービス選定	ある程度誘導あり	AIが決定
主な評価	Terraform/CI/CD	Architecture/Trade-off
正解	比較的明確	複数存在
人間の役割	承認・安全確認	設計レビュー・意思決定

なのでLEVEL3は、「Codexがクラウドエンジニアとして働けるか」から「クラウドアーキテクトとして働けるか」へ進む実験です。

今回の実験の延長なら、私はLEVEL3を3段階に分けるのが面白いと思います。

LEVEL3-A：単一クラウドArchitecture Design

例えばAWSだけ与えて、

この要件ならどんなArchitectureにする？

と聞きます。

AIにWell-Architected的な観点で、

Reliability
Security
Cost Optimization
Performance
Operational Excellence

を含めて設計させます。

ここではまだ実装しません。

LEVEL3-B：Multi-cloud選定

さらに難しくして、

AWS / Azure / GCPのどれを使うべきかも含めて設計してください

とします。

これがかなり面白いです。

AIが、

この要件ならCloud Runが有利なのでGCP

とか、

Microsoft Entra / M365との統合が強いためAzure

とか、

サービス成熟度と運用人材を考慮してAWS

という判断をできるかを見るわけです。

ここでは単純な機能比較ではなく、

「なぜそのクラウドなのか」

が重要になります。

LEVEL3-C：Architecture → 実装 → 障害 → 設計変更

これが最終形です。

例えばAIが最初に設計した環境を実際にTerraformで構築します。

その後、こちらから意地悪な条件を追加します。

アクセスが10倍になりました。

あるいは、

DB障害が発生し、2時間停止しました。

あるいは、

月額費用が想定の2倍になりました。

あるいは、

セキュリティ監査でPublic IPを禁止されました。

AIに、

原因分析
Architecture再設計
Terraform修正
Migration計画
無停止または最小停止で変更
Monitoring修正
コスト再評価

までやらせます。

ここまで来るとかなり実務に近いです。

今回のLEVEL2実験と綺麗につなげるなら、私は次のシナリオをおすすめします。

新しいB2C Webサービスを立ち上げる。

初期ユーザー1万人。
将来的には100万人。
日本国内サービス。
個人情報を扱う。
24時間365日サービス。
99.9%以上の可用性。
RTO 30分。
RPO 5分。
開発者5名。
インフラ専任1名。
初期インフラ費用10万円/月以内。

AWS / Azure / GCPのどれを使うかも含めて、
最適Architectureを設計してください。

重要なのは、サービス名を一切指定しないことです。

これでAIが、

VMを使うのか
Containerを使うのか
Serverlessを使うのか
Kubernetesを使うのか

から判断することになります。

そしてLEVEL3では「AIが動いたか」ではなく、評価表をかなり厳しくした方がいいです。

例えば、

要件理解
Architecture妥当性
Security
Availability
Scalability
Cost
Operations
DR
Observability
Complexity
Vendor lock-in
Migration容易性
人間の修正量

などを5段階評価します。

今回のLEVEL2では、かなり「AIは実装できる」という結果が出ました。

LEVEL3では逆に、

AIは合理的なArchitecture判断まで任せられるのか

を検証することになります。

そして個人的には、ここからが今回の実験で一番面白いところだと思います。
LEVEL2はCodexの「手」を試しましたが、LEVEL3は**設計者としての「頭」**を試すことになります。
